### 2026-09-23: 2019 SAS weight is segment-level, not plot-level
- **Decision:** Accept 2019 SAS weight variable (from PartIV_Agricultural practice.sav) as segment-level: one constant weight value per segment, varying across segments. This is structurally different from 2024+ which use plot-level `plot_weight`.
- **Reason:** Direct inspection of 2019 data: weight is labeled "Segment weight", is constant within each segment (verified across all ~2,800 unique segments), and exists only in the practice and fertilizer files, not in the production file where plot-crop data resides. This is consistent with a segment-sampling design followed by census of all plots within sampled segments. Attempting to treat it as plot-level would be incorrect and mislead the weighted ratio estimator.
- **Alternatives considered:** (1) Downweight or exclude 2019 from the pooled estimates. Rejected: segment-level weighting is valid for design-based inference; the issue is harmonization with later years, not invalidity of 2019 itself. (2) Derive a plot-level weight for 2019 by proportional allocation within segments. Rejected: would require plot-area proportionality assumptions and could introduce bias; better to document the structural difference and handle it at the estimation stage.
- **Reversible:** Yes. If the survey methodology changes to plot-level sampling in later years (confirmed by inspection), or if a methodologist determines that segment-level weights should be redistributed to plots, this can be revised. For now, it is a documented structural difference flagged in `docs/data/variable_audit.md` and in `config/sas_variable_map.yaml` comments.
- **Impact on pipeline:** The `src/agritwin/harmonize/` step must join the three 2019 files on (Segment_ID, plot_id) and attach the segment-level weight to every plot in the segment. When pooling 2019-2025 for district-level estimates, the weight column carries the design information (segments as PSUs); if future years use plot-level weights, the column definition must be clarified in the model card and variance estimation must be revisited.

### 2026-09-23: 2019 segment-level vs 2020+ plot-level weighting requires stratified design
- **Decision:** Estimate 2019 (segment-weighted) and 2020–2025 (plot-weighted) as separate design strata. Do not pool them naively.
- **Reason:** Survey methodologist review (2026-09-23) verified both designs are unbiased for point estimates but produce different variance structures. **Critical risk:** naive pooling using a single PSU bootstrap will underestimate variance in 2020+ because it ignores within-segment plot-level weight variation. Methodologist reported 2020 weight structure (77.8% of segments show variation across plots). Post-review individual verification of 2021–2025 computed: 2021 76.9%, 2022 76.0%, 2023 76.4%, 2025 ~76% segment weight variation, confirming the 2020–2025 block is homogeneous. This is contrasted with 2019: 1.6% of segments show weight variation (i.e., 98.4% constant), confirming segment-level design. The structural difference creates false precision risk: confidence intervals will be narrower than they should be if years are naively pooled, risking overconfident policy recommendations. Stratified design preserves 24k plots from 2019 (both seasons) for robust attainable-yield percentiles while respecting each year-block's actual design.
- **Alternatives considered:** (1) Harmonize 2019 to plot-level by proportional allocation (rejected: introduces bias if proportionality fails; loses design information). (2) Exclude 2019 (rejected: loses 12k plots/season, blocks nowcast backtests). (3) Advanced Hartley-Rao formula (rejected: too complex for 5.5-week timeline). Methodologist endorsed stratified approach as statistically sound and implementable.
- **Reversible:** Yes. If 2021-2023 audits reveal a multi-year block with segment weighting (2019–2021, say), the strata can be redrawn accordingly. If a future variance formula is developed to handle mixed designs, pooling could be revisited.
- **Impact on pipeline:** The `src/agritwin/survey/` module must accept a `design_year_blocks` parameter (e.g., {2019: 'segment', 2020–2025: 'plot'}) and compute separate design objects per block. Weighted ratio estimator and PSU bootstrap are computed independently per block; district-level results are labelled with design provenance ("2019 segment-weighted; 2020–2025 plot-weighted"). Export and web UI should surface this to users, avoiding the appearance of false precision.

### 2026-09-23: harvest_kg sources from s2q21, not s2q22, in every year
- **Decision:** Canonical `harvest_kg` in `stg_sas_plot_crop` is always sourced from s2q21 ("total quantity of harvest for this season"), never from s2q22 ("total quantity produced/to be produced by this crop this season"), across all 7 years.
- **Reason:** This was an open, unresolved question carried since the 2024 audit. Cross-tab run 2026-09-23 on pure-stand plots (2023, 2024, 2025 Season A) shows s2q21 and s2q22 are not equivalent: only 33-37% exact match, median relative difference ~33%, and the s2q22/s2q21 ratio is systematically greater than 1 (median 1.5x). The question wording explains this: s2q22 asks for quantity "produced/**to be** produced," which reads as projected or expected total production (including not-yet-harvested amounts), not the actual quantity harvested to date. Using s2q22 for a yield estimator would inflate actual yield with unharvested projections. s2q21 is also universally present across 2019-2025, while s2q22 as a separate crop-level column only exists 2023-2025, so using s2q21 avoids a second harmonization discontinuity on top of the 2019 weight-structure one.
- **Alternatives considered:** (1) Use s2q22 for 2023-2025 and s2q21 for 2019-2022 (rejected: introduces a within-schema definitional break exactly where the questionnaire gained a second harvest column, compounding interpretation risk for anyone comparing years). (2) Average or min(s2q21, s2q22) (rejected: fabricates a number with no basis in what was actually measured; the two questions measure different things, not the same thing with noise). (3) Leave harvest_kg null for years/rows where s2q21 is missing but s2q22 is present, rather than falling back to s2q22 (adopted as a corollary: no silent substitution across definitionally different fields).
- **Reversible:** Yes. If a later cross-tab against ground truth (e.g., AHS or a validation subsample) shows s2q22 is the better-calibrated field for a specific year, this can be revisited per year.
- **Impact on pipeline:** `src/agritwin/harmonize/` maps canonical `harvest_kg` from s2q21 only. s2q22 is not consumed anywhere in the harmonize output; it remains documented in `docs/data/variable_audit.md` as a rejected candidate, not as an alternate source.

### 2026-09-23: survey/ quality-flag thresholds (min_segments, cv_max)
- **Decision:** `config/settings.yaml`'s `survey.min_segments: 10` (unweighted PSUs below which a `district_yield` cell is `"suppressed"`, dropped entirely from `data/public/district_yield.csv`) and `survey.cv_max: 0.20` (yield CV above which a cell is `"use_with_caution"` but still published). Changed `cv_max` from its prior placeholder value of `0.30` to `0.20` for this specific use, since no other code consumed the old value (checked via `grep`) and 20% is the threshold this task specified.
- **Reason:** `min_segments: 10` is below the existing `n_min: 30` (unweighted *plots*), since segments aggregate multiple plots each; 10 segments is a common rule-of-thumb floor for having enough PSUs to trust a design-based variance estimate at all (fewer than that, the Taylor-linearized SE is itself unreliable, not just imprecise). `cv_max: 0.20` matches this task's explicit instruction. Both are first-pass MVP thresholds, not derived from a formal power calculation; real production run stats: of 1,779 crop x geography x season x year cells estimated, 868 (49%) were suppressed under `min_segments: 10` and 61 (3%) flagged `use_with_caution` under `cv_max: 0.20`, leaving 850 (48%) published as `"ok"`. That suppression rate is high enough to flag: MVP crop/district/season/year granularity is genuinely thin for several cells, expected given Rwanda has only 30 districts and the pure-stand restriction (see `docs/validation.md`) already excludes most plots.
- **Alternatives considered:** (1) A single combined "low_reliability" flag instead of separate `use_with_caution`/`suppressed` states (rejected: loses the distinction between "shown with a caveat" and "not shown at all," which `CLAUDE.md` golden rule 6 treats as different UI states). (2) A higher `min_segments` (e.g. 30, matching plot-level `n_min`) to reduce false confidence further (rejected for MVP: would suppress the majority of cells given the 49% rate already at 10; revisit once district-level demand is clearer).
- **Reversible:** Yes, both are `config/settings.yaml` values; changing them only requires re-running `make marts`.

### 2026-09-23: survey/ built on samplics despite its "archived, no longer maintained" notice
- **Decision:** Used `samplics.estimation.TaylorEstimator` as specified in `requirements.txt` and `docs/AgriTwin_Master_Build_Guide.md`, despite `samplics` printing a `FutureWarning` on import that the package is archived and recommends migrating to a package called `svy`.
- **Reason:** Not a live decision to make mid-implementation; `samplics` is the project's already-specified survey library, and swapping libraries mid-task is out of scope for this change. Documented here so it surfaces before release, not silently discovered later. Two real library quirks were worked around in `src/agritwin/survey/core.py`, not patched in the library itself: (1) `TaylorEstimator`'s internal CV computation divides `stderror / point_est` unconditionally and raises `ZeroDivisionError` on `0.0/0.0` for a domain where every sampled unit reports exactly 0 (a real "total crop failure" case in the data, not a bug); handled by estimating those domains separately with a manually-constructed zero-variance, undefined-CV row. (2) `to_dataframe()` returns a null `_domain` value when the input has exactly one unique domain, breaking a merge-on-domain join; patched by filling it back in from the known single domain value.
- **Alternatives considered:** None evaluated in this session (out of scope); noted as a candidate for the `svy` migration mentioned in samplics' own deprecation warning if this becomes a real maintenance burden post-hackathon.
- **Reversible:** Yes, `_taylor_total`/`_taylor_ratio` are the only two functions that call into samplics directly; swapping libraries later is localized to those two functions.

### 2026-09-23: Attainable yield zoning uses k-means, not an AEZ layer
- **Decision:** `config/settings.yaml`'s `attainable.zone_method` changed from its placeholder value `aez` to `kmeans`. Zones are k-means clusters (`k=5`, per existing `kmeans_k` setting) of Rwanda's 30 districts on standardized static features: `soil_ph`, `soil_nitrogen`, `soil_carbon`, `soil_texture_class` (iSDAsoil, via the GEE mart) and `cropland_fraction` (ESA WorldCover). `random_state=0` fixed for reproducibility.
- **Reason:** No agro-ecological zone boundary layer is configured anywhere in this repo: checked `config/data_sources.yaml` (no AEZ entry among the GEE datasets) and `data/external/` (no AEZ file). This is exactly the situation `docs/AgriTwin_Master_Build_Guide.md` section 4.1 already anticipates ("or a k-means zoning if an AEZ layer isn't readily available"), so the documented fallback was used rather than sourcing a new AEZ dataset mid-task (no known source was already vetted for this project) or leaving `zone_method: aez` pointing at a layer that doesn't exist.
- **Alternatives considered:** (1) Source a real AEZ layer (e.g. FAO's GAEZ or a Rwanda-specific agro-ecological zone map) via Earth Engine or a new download. Rejected for this pass: not already vetted or added to `config/data_sources.yaml`, and out of scope for the immediate goal (attainable yield needs *a* reasonable zoning to compute against, not necessarily the ideal one on the first pass). (2) Zone at plot level directly instead of district level. Rejected: the only zoning-relevant covariates available (soil, cropland fraction) are already only available at district granularity from the existing GEE mart; plot-level soil data was never extracted.
- **Reversible:** Yes. `assign_zones()` is a single, isolated function; swapping in a real AEZ layer later only requires replacing that function's input, not `compute_attainable_yield`/`compute_yield_gap`.

### 2026-09-23: No confidence interval on attainable yield (percentile), only a reliability flag
- **Decision:** `models/attainable.py`'s weighted 90th percentile carries a `"suppressed"`/`"ok"` reliability flag (same `min_segments` logic as `survey/`), not a confidence interval.
- **Reason:** `samplics.estimation.TaylorEstimator` does not expose an arbitrary-percentile Taylor-linearized variance (`PopParam` only offers `median`, not a general quantile), and implementing a PSU bootstrap specifically for a 90th-percentile CI is real additional scope not requested for this pass. A segment-count suppression flag still satisfies `CLAUDE.md` golden rule 6's requirement that every displayed number carry an interval *or* a reliability flag.
- **Alternatives considered:** (1) Use `PopParam.median` as a proxy and manually shift. Rejected: not statistically equivalent to a real 90th-percentile CI, would misrepresent precision. (2) Implement a PSU bootstrap now. Deferred, not rejected: worth doing before this is presented as a judged, citable statistic, flagged here so it isn't forgotten.
- **Reversible:** Yes, additive; a bootstrap CI can be added to `compute_attainable_yield`'s output later without changing its existing columns.

### 2026-09-24: Excluded suppressed cells from nowcast training and evaluation (external review, Step 3)
- **Decision:** `src/agritwin/models/nowcast.py`'s `exclude_low_reliability()` drops rows where `reliability == "suppressed"` (fewer than `survey/`'s `min_segments`, currently 10) from both the training and evaluation population in `leave_one_year_out_cv`. `use_with_caution` rows are kept. `prior_season_yield_kg_ha` is not affected by this filter: it is still looked up from the full unfiltered table (`build_yield_lookup`), since it is an input feature representing the best information a real forecaster would have had, not the target being modeled.
- **Reason:** `data/marts/district_yield.parquet` showed 56% of all district-level rows (800 of 1,425) are `"suppressed"`, and the rate is wildly uneven by crop: maize 66%, irish_potato 73%, sorghum 48%, beans 25%. This matches exactly what the external review flagged: the two crops with the worst nowcast MAPE (maize, irish_potato) are also the two with the highest suppression rates. Checked row counts before implementing: after exclusion, every crop retains at least 58 rows per fold in leave-one-year-out training (well above the 20-row floor), so the fix was implementable without starving the model of data; the real cost is smaller test sets in thin years (as few as 3-9 rows for some crop-years), which affects the precision of individual year folds, not the overall approach's feasibility.
- **Result: MAPE drops dramatically and uniformly, and the model-vs-baseline picture changes materially.** `baseline_district_mean` MAPE alone: maize 54.3% to 28.4%, beans 24.5% to 20.6%, irish_potato 43.2% to 14.4%, sorghum 30.1% to 21.0%. Maize and irish_potato mostly still favor the naive baseline. Full before/after table: `data/public/nowcast_backtest.csv` (current) vs the version at commit `01795f1` (before this fix, in git history).
- **Alternatives considered:** inverse-variance weighting using `yield_kg_ha_se` (also available in the mart). Not chosen: given how extreme the suppression rate is for two crops (66-73%), a weighting scheme would still leave many near-zero-weight rows physically present, adding complexity (sample-weighted fits for both models, a decision on whether the reported MAPE itself should be weighted, guards against zero/NaN SE) without a clear accuracy benefit over the simpler exclusion, which is also consistent with how "suppressed" is already treated everywhere else in this codebase.
- **Reversible:** Yes. `exclude_low_reliability()` is a single, isolated, pure function.
